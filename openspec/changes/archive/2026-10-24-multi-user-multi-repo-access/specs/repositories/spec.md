# Spec Delta

## Purpose

Lets one multi-user server host several independent Git-backed knowledge bases: how repositories are registered and removed, how they stay isolated from each other, how their credentials are kept, and how clients address them through one path tree.

## ADDED Requirements

### Requirement: Repository registry
In multi-user mode the server SHALL keep a registry of repositories, each with a unique alias, a Git remote URL, a branch and a credential. The registry SHALL survive restarts and MAY be empty. An alias SHALL be 1 to 32 characters of lowercase letters, digits and hyphens, starting with a letter or digit, and SHALL NOT change after creation.

#### Scenario: Restart
- **WHEN** the server restarts with two registered repositories
- **THEN** both are served again without being added again

#### Scenario: Empty registry
- **WHEN** the server runs in multi-user mode with no repositories
- **THEN** it starts, the root listing is empty, and the administrator can add a repository

#### Scenario: Invalid alias
- **WHEN** a repository is added with the alias `My Notes`
- **THEN** it is rejected with an explanation of the allowed form

### Requirement: Adding a repository
The administrator SHALL be able to add a repository by giving an alias, a remote URL, a branch (default `main`) and a credential: an access token for an `https://` URL, or an SSH key for an SSH URL (`ssh://` or `user@host:path`). Any other URL form, and a URL that embeds credentials, MUST be rejected. The server SHALL clone the repository in the background, and a failed clone SHALL leave it registered so the credential or URL can be corrected.

#### Scenario: Successful add over HTTPS
- **WHEN** the administrator adds a reachable `https://` repository with a valid token
- **THEN** its status moves from `cloning` to `ok`, and its notes become listable and searchable under its alias for accounts that are given access

#### Scenario: Successful add over SSH
- **WHEN** the administrator adds `git@example.com:org/notes.git` with a key the remote accepts
- **THEN** its status moves from `cloning` to `ok`

#### Scenario: Wrong token
- **WHEN** the administrator adds a repository with a token the remote rejects
- **THEN** the status becomes `error` with a reason that does not contain the token, and no notes are served for it

#### Scenario: Credentials inside the URL
- **WHEN** the URL is `https://user:secret@example.com/org/notes.git`
- **THEN** the request is rejected and nothing is stored

#### Scenario: Unsupported URL form
- **WHEN** the URL is `http://example.com/org/notes.git`, `file:///srv/notes` or starts with `-`
- **THEN** the request is rejected and nothing is stored

#### Scenario: Credential does not match the URL
- **WHEN** an SSH URL is submitted with an access token, or an `https://` URL with an SSH key
- **THEN** the request is rejected with an explanation

#### Scenario: Duplicate alias
- **WHEN** a repository is added with an alias that is already registered
- **THEN** the request is rejected and the existing repository is unaffected

### Requirement: Repository status
Every repository SHALL report one status: `key_pending` (a generated SSH key awaits confirmation), `cloning`, `ok`, `offline`, `conflict`, `error` (with a reason that contains no credential) or `credential_invalid`. A repository that is not `ok`, `offline` or `conflict` SHALL serve no notes.

#### Scenario: Failed clone
- **WHEN** a clone fails because the remote does not exist
- **THEN** the status is `error` with a reason, the repository stays registered, and its alias answers `not_found`

### Requirement: A new repository is visible to nobody
Adding a repository SHALL create no access rules. Until the administrator creates rules for it, the repository SHALL be absent from every account's root listing and searches, the administrator's included.

#### Scenario: Freshly added repository
- **WHEN** a repository has just reached the status `ok` and no rules refer to it
- **THEN** no account, the administrator included, can list, read or search it

### Requirement: SSH keys for repositories
For an SSH URL the administrator SHALL choose between a key generated by the server and an existing private key supplied in the request. A generated key SHALL be unique to that repository, and its private part MUST NOT be shown or exported. A supplied key MUST be rejected when it is malformed or protected by a passphrase. The public key and its fingerprint SHALL be available to the administrator at any time, so the key can be registered with the Git host.

#### Scenario: Generated key
- **WHEN** the administrator adds an SSH repository and asks the server to generate a key
- **THEN** the public key is shown, the repository stays in the `key_pending` state without contacting the remote, and the clone starts once the administrator confirms that the key is registered

#### Scenario: Supplied key
- **WHEN** the administrator supplies a valid unencrypted private key
- **THEN** it is stored, its public key and fingerprint are shown, and the private key is never shown again

#### Scenario: Passphrase-protected key
- **WHEN** the administrator supplies a private key protected by a passphrase
- **THEN** the request is rejected with an explanation and nothing is stored

### Requirement: SSH host keys are pinned
The server SHALL keep its own list of known SSH host keys. A host contacted for the first time SHALL be recorded, unless host keys were provided through `KB_SSH_KNOWN_HOSTS`, in which case only those SHALL be trusted. WHEN a host presents a key different from the recorded one, the server MUST NOT connect and SHALL put the repository in the `error` state with a reason naming the host.

#### Scenario: First contact
- **WHEN** an SSH repository on a host never contacted before is added
- **THEN** the host key is recorded and the clone proceeds

#### Scenario: Host key changed
- **WHEN** a host later presents a different key
- **THEN** synchronisation of repositories on that host stops with status `error`, and nothing is sent to it

### Requirement: Removing a repository
Removing a repository SHALL stop serving it, delete its local clone and index, and delete every access rule that refers to it. The server MUST NOT modify or delete anything on the remote. Local commits not yet pushed SHALL be pushed first when the remote is reachable; otherwise the removal SHALL require an explicit confirmation that unpushed work will be lost.

#### Scenario: Remove a synced repository
- **WHEN** the administrator removes a repository whose local history is fully pushed
- **THEN** its paths answer `not_found`, its local files are gone, and the remote is unchanged

#### Scenario: Unpushed work
- **WHEN** a repository has local commits that cannot be pushed and removal is requested without the confirmation
- **THEN** the removal is refused with the number of unpushed commits

### Requirement: Repositories are isolated
Each repository SHALL have its own clone, search index, write lock, synchronisation schedule and conflict state. A failure, an unresolved merge or a slow operation in one repository MUST NOT block reads or writes in another.

#### Scenario: Conflict in one repository
- **WHEN** repository `a` has an unresolved merge and a client writes a note in repository `b`
- **THEN** the write in `b` succeeds, and a write in `a` fails with `merge_conflict`

#### Scenario: Unreachable remote
- **WHEN** the remote of repository `a` is unreachable
- **THEN** `a` reports `offline` and repository `b` keeps synchronising normally

### Requirement: Repository credentials are encrypted at rest
Repository access tokens and SSH private keys SHALL be stored only in encrypted form, using a key supplied through `KB_SECRET_KEY` and never stored by the server. A credential MUST NOT be returned by any interface after it is submitted or generated; only the last four characters of a token, or the public key and fingerprint of an SSH key, MAY be shown. An undecryptable credential SHALL NOT prevent the server from starting.

#### Scenario: Token never read back
- **WHEN** the administrator opens a repository's settings after adding it
- **THEN** only the last four characters of the token are shown

#### Scenario: State file inspection
- **WHEN** the state file is read on disk
- **THEN** it contains neither a token nor a private key in clear text

#### Scenario: Secret key replaced
- **WHEN** the server starts with a different secret key than the one used to store a credential
- **THEN** it starts, that repository reports `credential_invalid`, and the others are unaffected

### Requirement: Decrypted SSH keys stay off the data volume
WHEN Git needs an SSH private key as a file, the server SHALL keep the decrypted copy only in a private directory outside the data volume, readable by the server's own user only, and SHALL delete it when the repository is removed and when the server stops.

#### Scenario: Data volume inspection while running
- **WHEN** the data volume is searched while an SSH repository is being synchronised
- **THEN** no file on it contains the private key in clear text

#### Scenario: Shutdown
- **WHEN** the server stops cleanly
- **THEN** no decrypted key file remains

### Requirement: Configured vault becomes the first repository
WHEN the server starts in multi-user mode with an empty registry and a vault configured through the existing settings, it SHALL register that vault as a repository under the alias from `KB_VAULT_ALIAS` (default `main`), reusing the existing clone, index and Git credentials in place, and SHALL create one ordinary access rule giving the administrator `write` on its root. This import SHALL happen once.

#### Scenario: Switching an existing deployment
- **WHEN** a deployment with a populated vault volume is restarted with an administrator address
- **THEN** the vault is served under `main/` without a new clone and without a full reindex, the administrator can read and write it, and no other account can see it

#### Scenario: Import rule is an ordinary rule
- **WHEN** the administrator clears its own rule on the imported repository
- **THEN** the administrator can no longer see that repository

#### Scenario: Later restarts
- **WHEN** the imported repository is removed by the administrator and the server restarts
- **THEN** it is not imported again

### Requirement: Unified path tree
In multi-user mode every path accepted or returned by a tool, resource or signed link SHALL start with a repository alias followed by the path inside that repository. The empty path SHALL denote the root, whose children are the repositories. A path whose first segment is not a registered repository SHALL fail with `not_found`. Files cannot be created at the root.

#### Scenario: Reading a note
- **WHEN** a client reads `notes/Projects/plan.md`
- **THEN** it receives `Projects/plan.md` from the repository with alias `notes`, and the returned path is `notes/Projects/plan.md`

#### Scenario: Root listing
- **WHEN** a client lists the root
- **THEN** each entry is a folder named after a repository

#### Scenario: Unknown alias
- **WHEN** a client reads `nope/a.md` and no repository has the alias `nope`
- **THEN** the call fails with `not_found`

#### Scenario: Write at the root
- **WHEN** a client creates the note `plan.md` with no alias
- **THEN** the call fails with `invalid_path`

### Requirement: Operations stay inside one repository
A single write SHALL affect exactly one repository. Moving a note or file between repositories SHALL fail with `invalid_argument`. Wikilinks and relative links SHALL resolve only within the repository of the note that contains them.

#### Scenario: Move across repositories
- **WHEN** a client moves `a/x.md` to `b/x.md`
- **THEN** the call fails with `invalid_argument` and nothing changes

#### Scenario: Same note name in two repositories
- **WHEN** `a/Note.md` contains `[[Target]]` and both `a/Target.md` and `b/Target.md` exist
- **THEN** the link resolves to `a/Target.md`, and backlinks of `b/Target.md` do not include `a/Note.md`

### Requirement: Search spans repositories
Search, grep, structured query, quick open, context bundles and tag listing SHALL cover every repository available to the caller and SHALL return alias-prefixed paths. A folder filter SHALL narrow the operation to one repository or a folder inside it. Limits, offsets and sorting SHALL apply to the combined result.

#### Scenario: Search across two repositories
- **WHEN** both `a` and `b` contain a note matching `budget` and a client searches `budget` with no filter
- **THEN** results from both repositories are returned in one ranked list

#### Scenario: Narrowing to one repository
- **WHEN** the same search is run with folder `a`
- **THEN** only notes under `a/` are returned

### Requirement: History tools address one repository
Tools that take a revision (`kb_log`, `kb_history`, `kb_ls_tree`, `kb_show_revision`, `kb_diff`, `kb_restore`) SHALL determine the repository from their path or folder argument, and revisions SHALL be interpreted in that repository. WHEN the argument is absent and more than one repository is available to the caller, the call SHALL fail with `invalid_argument` listing the available aliases.

#### Scenario: Log of one repository
- **WHEN** a client calls `kb_log` with folder `notes`
- **THEN** only commits of the repository `notes` are returned

#### Scenario: Ambiguous log
- **WHEN** a client with access to two repositories calls `kb_log` without a folder
- **THEN** the call fails with `invalid_argument` and the message lists both aliases

#### Scenario: Single repository
- **WHEN** a client with access to exactly one repository calls `kb_log` without a folder
- **THEN** that repository's commits are returned

### Requirement: Classic mode keeps one unprefixed vault
In classic mode the server SHALL serve exactly the configured vault with paths relative to its root, no alias segment and no repository registry.

#### Scenario: Classic paths
- **WHEN** a classic-mode client reads `Projects/plan.md`
- **THEN** the note at that vault-relative path is returned, as before this change
