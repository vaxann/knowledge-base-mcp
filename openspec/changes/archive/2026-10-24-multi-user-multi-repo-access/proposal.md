# Proposal

## Why

The server today serves one vault to one identity: a shared static token and a single sign-in password, and whoever passes sees and can change everything. Sharing a knowledge base with other people, or serving several knowledge bases from one instance, is impossible without handing out full access. This change adds named accounts, several repositories and per-folder access rules so one deployment can serve a small group safely.

## What Changes

- **Multi-user mode**, opt-in by configuring an administrator address (`KB_ADMIN_EMAIL`) on the HTTP transport. Without it the server behaves exactly as today (classic mode: one vault, static token, password sign-in, unprefixed paths). stdio is always classic.
- **Accounts with email sign-in.** In multi-user mode the OAuth sign-in page asks for an email address and a 6-digit one-time code delivered by email through the Resend HTTP API. No passwords. Accounts are created by the administrator only; there is no self-registration. Every issued token belongs to one account.
- **Break-glass token.** In multi-user mode `KB_HTTP_TOKEN` keeps working as a bearer token of the administrator account and as a recovery sign-in for the admin panel, so a mail outage cannot lock the administrator out.
- **Several repositories.** The administrator adds Git repositories at runtime: a short alias, a branch, and either an HTTPS URL with an access token or an SSH URL with a key (generated by the server or supplied). Each has its own clone, search index, sync loop and conflict state. The vault from the existing configuration is imported as the first repository.
- **BREAKING (multi-user mode only): unified tree.** Every path gains the repository alias as its first segment (`notes/Projects/plan.md`). The root listing shows repositories; search spans all repositories the caller can read.
- **Folder-level access rules.** A rule is (account, repository, folder, level) with levels `none`, `read`, `write`. Rules inherit downwards and the deepest rule wins, so a subfolder can be closed inside an open folder. Anything a caller cannot read does not exist for them (`not_found`) in every tool, resource, history view and signed link. The administrator has no implicit access to content: a new repository is visible to nobody until rules are created, and the administrator grants itself access like anyone else. A new error code `forbidden` reports a write to a readable but not writable path.
- **Admin panel** at `/admin`: accounts (create, disable, revoke sessions, delete), repositories (add, replace credential, status, sync, remove), access rules (folder tree with a level per account).
- **Server-side state.** Accounts, rules, repositories and OAuth data move into one state file on the data volume. Repository tokens and SSH private keys are stored encrypted with a key from `KB_SECRET_KEY`; they are write-only in the panel.
- **Acting user in history.** Commits keep the shared author and gain a `KB-User` trailer.
- New configuration: `KB_ADMIN_EMAIL`, `KB_RESEND_API_KEY`, `KB_MAIL_FROM`, `KB_SECRET_KEY`, `KB_DATA_DIR`, `KB_VAULT_ALIAS`.

Non-goals: personal API tokens for non-OAuth clients, repositories added by non-administrators, additional administrators, renaming a repository alias, file-level (as opposed to folder-level) rules, passphrase-protected SSH keys, accounts or several repositories over stdio.

## Capabilities

### New Capabilities
- `user-accounts`: multi-user mode activation, accounts, email one-time-code sign-in, binding of tokens to accounts, the break-glass administrator token.
- `repositories`: the registry of Git repositories, their lifecycle and isolation, credential storage, the unified path tree and cross-repository behavior of tools.
- `access-control`: access rules, their evaluation, and enforcement across every tool, resource, history view and signed link.
- `admin-panel`: the administrator web interface for accounts, repositories and access rules.

### Modified Capabilities
- `mcp-transport`: OAuth sign-in uses the email code in multi-user mode; `kb_info` reports repositories instead of one vault path.
- `vault-access`: paths carry a repository alias in multi-user mode; the server may hold encrypted repository credentials (tokens and SSH keys) in its state file.
- `git-versioning`: sync status and manual sync become per repository; commits carry a `KB-User` trailer.

These three capabilities are defined by the completed but not yet archived change `bootstrap-knowledge-base-mcp`; that change must be archived before this one so the deltas have main specs to apply to.

## Impact

- **Code**: new packages for the state store, accounts and sign-in codes, mail delivery, access rules, the repository workspace and the admin panel; `internal/oauth` gains a pluggable sign-in step and per-account tokens; `internal/mcpserver` resolves the caller per request and talks to the workspace instead of one service; `internal/kb` gains visibility filtering hooks in listing, search, links and history; `internal/config` gains the new settings; `cmd/knowledge-base-mcp` wires the two modes.
- **APIs**: in multi-user mode tool paths are alias-prefixed, `kb_info`, `kb_sync_status`, `kb_sync_now`, `kb_conflicts` and `kb_reindex` become repository-aware, and `forbidden` joins the stable error codes. Classic mode is unchanged.
- **Dependencies**: no Go modules added. Mail goes through `net/http`; encryption uses the standard library; SSH key generation and validation use the `ssh-keygen` binary that already ships in the image next to `git`.
- **Operations**: multi-user deployments need a Resend API key with sending access, a verified sending domain, a sender address, and a secret key. After the switch the imported vault is visible to the administrator only. Existing OAuth tokens are invalidated when a deployment switches to multi-user mode; registered clients are kept and simply sign in again.
- **Docs**: README, `docs/configuration.md`, `docs/clients.md`, `.env.example`, `config.example.yaml`, plus a new `docs/multi-user.md`.
